# 2026-08-21 · 批量入库 8 份年报 + Golden Set v0 两阶段评测

> 对应提交：`feat: 年报批量入库与 Golden Set 两阶段评测`
> 背景：知识库只有 1 份年报摘要，无法验证跨公司检索；所有优化（GPU、分流、调参）都缺一把可量化的尺子。

## 做了什么

1. **批量入库 8 份完整年报**（福建金森/新纶新材/青岛中程/万向钱潮/申能股份/永安林业/金正大/ST西发，共约 1600 页）：走新上传任务 API，一个 job 串行处理，进度全程可轮询。
2. **Golden Set v0 + 两阶段评测框架**：
   - `eval/build_golden.py`：从每份已入库文档的 `layout.json`（解析器落盘的结构化元素）自动提取事实——近 3 年主要会计数据表的营收/归母净利润（含页码）、"可能面对的风险"章节页、"利润分配"章节页——生成带期望文档/期望页码的题目，外加 2 道拒答题（库里不存在的公司）。
   - `eval/run_eval.py` 重写为两层：**检索层**（`--tier retrieval`，不耗 LLM）测 doc_hit@5 / page_hit@5 / MRR；**答案层**（`--tier answer`）测关键词命中、拒答准确性、引用率。默认只跑检索层，秒级出分。

## 用了什么技术

- **事实提取三防**：① 优先"近 3 年"表（否则会把分季度表的单季营收当年报数）；② 标签去空格归一化（docling 会在长单元格插空格："归属于上市 公司股东的 净利润"）；③ 章节定位只认标题元素且跳过前 3 页目录区。
- **期望值即解析产物**：题目期望页码来自 layout.json 的元素页码——检索层测的是"能否召回解析器认为的事实位置"，与 LLM 无关，跑一次几秒钟。
- **软拒答判定**：置信控制拒答（证据分低于阈值）置 `refused` 标志；但"库里没有茅台"这类问题证据分够高、由 LLM 依据资料声明"无法确认"——同样是不编造的正确行为，评测按"标志或答案含无法声明"计入。

## 解决了什么问题（效果怎么样）

**入库吞吐实测**：完整年报约 17-20 分钟/份（160-240 页 × 4.4s/页 CPU 版面模型），首批 4 份入库 4433/1793/1578/? 块。这是 GPU 验证必要性的直接量化（预期 5-10 倍后单份 2-4 分钟）。

**Golden Set 最终基线**（9 份文档 34 题：32 道事实题 + 2 道拒答题；中间基线 5 文档 18 题见 git 历史）：

| 指标 | 5 文档时 | **9 文档（最终）** | 说明 |
| --- | --- | --- | --- |
| doc_hit@5 | 1.00 | **1.00** | 公司名路由在库扩容后依然完美，32/32 |
| evidence_hit@5 | 0.75 | **0.53** | 库变大后精确证据排序明显退化（12/32） |
| page_hit@5 | 0.56 | 0.34 | 严格位置指标，诊断用 |
| MRR | 0.92 | 0.86 | |
| 答案层 keyword_hit | 0.75 | 0.63 | |
| 拒答准确性 | 0.83 | 0.65 | 茅台/腾讯拒答题本身 2/2 正确；答案题因检索缺口被动拒答拉低 |
| 检索延迟 | 0.67s | **0.48s/题** | 检索层全量 32 题 15 秒跑完 |

入库总量：8 份完整年报全部成功（1061~2125 块/份，总 13,039 块），单份耗时 17-26 分钟。

**三个真实发现**（这就是 Golden Set 的价值）：
1. **精确数字块排序偏弱，且随库变大恶化**（evidence_hit 0.75→0.53）：15 个未命中里 14 个是数字题，且期望页常在 top-5 里——只是含目标行的那一个表格分片排在同页兄弟分片之后（长表按行拆分后，"营业收入"行所在分片与同表其他分片竞争力相同）。调优方向：① rerank 对含查询关键词精确行（如"营业收入"+数字模式）的分片加权；② 或对"主要会计数据"这类高价值小表不拆分。
2. **docling 断数字**：长数字被拆成"14,486,808,9 20.82"，降低数值保真度。管线级修复（解析后重组数字+重灌）留待 GPU 验证后与全量重灌一起做。
3. **评测指标要跟语义对齐**：拒答标志只覆盖置信控制路径（软拒答判定解决）；答案关键词子串匹配对单位换算（万元）不容差（记录为已知限制）。

## 解决了什么问题（效果怎么样）

- 入库吞吐实测：**完整年报约 17-20 分钟/份**（160-240 页 × 4.4s/页 CPU 版面模型），8 份串行约 2.5 小时——这是 GPU 验证必要性的直接量化（预期 5-10 倍提速后单份降到 2-4 分钟）。
- 评测闭环：检索层 1.4 秒/题、答案层 4.5 秒/题；冒烟集（东吴证券摘要 2 题 + 2 拒答题）doc_hit/page_hit/MRR 全 1.0，拒答 2/2 正确（软判定）。
- 提取正确性：东吴证券营收取值 11,280,990,458.17（第 8 页）与此前人工问答验证的数字完全一致。

## 遇到的问题与该怎么办

| 问题 | 根因 | 应对（通用方法） |
| --- | --- | --- |
| 评测脚本 ModuleNotFoundError: src | `python eval/run_eval.py` 只把脚本目录加进 sys.path，不加 cwd | 脚本头部显式 `sys.path.insert(项目根)`。**方法：可执行脚本一律自带路径引导，不依赖调用目录** |
| 营收取到分季度表的值（2,254,473,360.84 ≠ 11,280,990,458.17） | "主要会计数据"章节下有多张表，后处理的表覆盖了前面的 | 候选表按"近 3 年"优先排序且每键只取首个命中。**方法：从文档提取事实时先枚举同章节的所有候选，明确优先级再取值** |
| 净利润行匹配不到 | docling 在长单元格文本里插空格，`startswith("|归属于上市公司股东的净利润")` 失配 | 匹配前做去空格归一化，取值用原始行 |
| 拒答准确率虚低（0.5） | `refused` 标志只覆盖置信控制路径，LLM 层的"库里没有"拒答不计 | 评测指标与产品语义对齐：不编造=对，用软拒答判定。**方法：评测指标必须先弄清被测标志的确切语义，别按名字猜** |
| 写入含中文引号的 Python 文件语法错误 | heredoc/编辑过程中弯直引号混淆 | 重写整文件；之后涉及代码的 heredoc 只用 ASCII 引号，中文引号仅出现在字符串内容里 |
