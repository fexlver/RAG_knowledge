# 2026-08-21 · Docling Spike 结论详解（写给不熟悉解析领域的自己）

> 配套阅读：[2026-08-21-Docling解析Spike.md](2026-08-21-Docling解析Spike.md)（实验记录本体）。本文解释那些结论**背后的原理**，看懂了才能在面试/复盘时讲清楚。

## 〇、两个基础概念

**① PDF 分两种形态**：

- **数字原生**：Word/排版软件直接导出的 PDF，文字以"文本对象"存在文件里，可选中复制，每个字自带精确坐标；
- **扫描件**：每页其实是一张照片（扫描仪/手机拍的），文件里没有文字，只有像素。想拿文字必须 OCR（图像识别）。

判断一份 PDF 是哪种：选中一段文字能复制出来就是数字原生。巨潮下载的年报都是数字原生。

**② Docling 转换一页时实际发生的步骤**：

1. 读 PDF 文本层，拿到这页所有文字和坐标；
2. 把整页**渲染成一张图片**；
3. **版面模型**（深度学习模型）看这张图，判断哪里是标题、正文、表格、图片、页眉页脚——输出一堆"元素框"；
4. **TableFormer**（另一个深度学习模型）对每个识别出的表格区域再单独推理一次，恢复行列结构（表头在哪、哪个单元格跨行跨列）；
5. **OCR**（RapidOCR）只对"位图区域"（照片、扫描页）识别文字；
6. 把以上结果组装成树形文档结构，每个元素都带页码和坐标（prov 溯源字段）。

记住这个关键：**第 3、4 步是深度学习模型推理，不管什么文档每页都必跑**。这就是耗时的来源。

## 一、"实测 4.3–4.5 秒/页，预算 0.1–0.5 秒/页"差在哪

原预算的假设是："数字原生 PDF 免 OCR，解析就是抽文本，很快"——如果只抽文本，确实 0.1 秒都不用。

但 Docling 标准管线的价值不是"抽文本"，而是**理解版面**（第 3、4 步）。为了拿到标题层级和表格结构，每页必须跑两个神经网络。深度学习模型推理 = 海量矩阵乘法：

- **CPU**（几十个强核心）做矩阵运算是"几个人排队搬砖"；
- **GPU**（几千个小核心）是"几千人同时搬砖"。

所以 CPU 上一页 4 秒多，GPU 上预期 0.5 秒以内（待验证）。

**年报还是最坏情况**：694 页里 1207 个表格，平均每页 1.7 个，TableFormer 要单独跑 1207 次。纯文字文档会明显快于 4.4 秒/页，但版面模型那部分的底价躲不掉。

换算成体感：一份 200 页年报 ≈ 15 分钟（单进程）。

## 二、对照实验：怎么证明"瓶颈不是 OCR"

**直觉**会说：OCR 是图像识别，应该最慢。**直觉不可靠，做对照实验**：

- 实验设计：同一批 3 份文档跑两轮，唯一变量是 `do_ocr` 开/关，其他全部一致；
- 结果：694 页合计，关 OCR 3073.2s，开 OCR 3102.3s，**差 29.1 秒（0.9%）**。第三份开 OCR 甚至更快——这个"反常"说明差异已在机器噪声范围内（同一段代码跑两遍时间本来就会浮动 1-2%）。

**为什么 OCR 几乎免费**：数字原生页的文字已经在文本层里（第 1 步拿到了），Docling 默认策略是"只对位图区域跑 OCR"——数字原生页没有位图区域，OCR 根本没启动。29 秒大概是零星几个图片区域（3 份合计才 6 张图）的识别时间。

**工程结论**：主链路 `do_ocr=True` 常开。万一某份"看着是数字原生"的文件混进扫描页，OCR 自动兜住，而代价趋近于零。这种"默认开也不亏的保险"要开。

## 三、"150 天"的算术与三档分流

**算术**：10 万份 × 平均 30 页 = 300 万页；300 万 × 4.4 秒 ≈ 1320 万秒 ≈ **153 天**（单进程不眠不休）。这 obviously 不可接受。

三条出路（不互斥，可叠加）：

1. **多 worker 并行**：worker = 一个独立进程，各自处理不同文档，互不干扰。8 个 worker ≈ 19 天，16 个 ≈ 10 天。代价：占满 CPU，机器干不了别的；
2. **GPU 推理**：版面模型和 TableFormer 换到 GPU 跑，预期 5-10 倍（待验证）。本机有 RTX 5060，装 CUDA 版 torch 即可；
3. **三档分流（最划算）**：不是所有文档都值得上全管线。

三档分流长这样：

| 档位 | 走什么 | 成本 | 适用 |
| --- | --- | --- | --- |
| 档 1：轻量直取 | 只抽文本层 + 粗切块，跳过一切模型 | ~0.1-0.5 s/页 | 纯文字的合同、通知、简单报告 |
| 档 2：标准管线 | Docling 全套（版面+表格+可选 OCR） | ~4.4 s/页 | 需要标题层级/表格结构/精确溯源的文档 |
| 档 3：OCR 管线 | 标准管线 + 全页 OCR | 更高 | 扫描件、图片型 PDF |

**入队时怎么判定走哪档**：算几个便宜信号——文本层字符覆盖率（一页能直接抽出多少字）、图片区域占比、总页数。成本几乎为零，在文档进队列时算一次。

类比：医院分诊（triage）。感冒的拿药走人，重伤的进 ICU，不能所有人都进 ICU——ICU（深度模型管线）资源贵，要留给真正需要的。

原方案是两档（数字原生/扫描件），实测数据证明这个分法不够：**数字原生内部也要再分**，因为"数字原生但版面简单"的文档占了企业文档的大头，为它们跑 4.4 秒/页是浪费。

## 四、中文路径问题与 DocumentStream

**问题**：docling-parse（Docling 底层的 C++ 原生库，用 C++ 是为了解析速度）在 Windows 下无法加载路径里含中文的文件。我们的语料文件名是 `000010_美丽生态_2023.pdf`，3 份全部加载失败。

**排查过程（这本身就是方法论）**：

1. 直接传中文路径 → 失败（C++ 库的 Windows 编码问题）；
2. 换成纯英文路径的同一份文件 → 成功 → 确认是路径问题而非文件问题；
3. 直接传 `BytesIO`（内存字节流）→ 被 pydantic 校验拒绝（Docling 的输入模型期望文件路径或 HTTP 来源，不认裸字节流）；
4. 用 `DocumentStream(name=..., stream=io.BytesIO(path.read_bytes()))` 包装 → **成功**。

`DocumentStream` 的意思就是"给一串字节起个文件名"，Docling 把它当作一个虚拟文件读。文件内容先完整读进内存（`path.read_bytes()`），再交给解析器，全程不经过带中文的文件路径。

**为什么说"和 MinIO 天然一致，不是权宜之计"**：MinIO 是对象存储（企业方案里存原始文件的组件，类似自建的阿里云 OSS）。从对象存储取文件的方式是 HTTP 请求**拿回一串字节**，本来就不落地成本地文件。所以"解析器从字节流读输入"正是目标架构的正确姿势——本地开发阶段被迫用的绕路，恰好就是生产架构的标准形态。这种巧合值得记下来：**约束逼出来的方案有时比原方案更对**。

## 五、每个产物是干嘛的

| 产物 | 是什么 | 什么时候用 |
| --- | --- | --- |
| `scripts/spike_docling.py` | 可复跑的实验脚本。`--no-ocr`/`--tag` 就是对照实验的变量控制和分组 | 换语料/换参数/换机器重测，直接改参数复跑 |
| `output/docling-spike-*/markdown/*.md` | 解析结果的**人类可读投影**（把树形结构摊平成 markdown） | 人工抽查质量——我验证表格重建就是肉眼看这些文件 |
| `output/docling-spike-*/json/*.json` | 结构化 DoclingDocument 全量导出，**含 prov（页码+坐标）** | 未来入库的真正数据源；溯源高亮靠它 |
| `output/docling-spike-*/stats.csv` | 每份文档一行：页数/表格数/耗时/元素统计 | 横向比较不同文档、不同配置 |
| `output/docling-spike-*/summary.json` | 汇总指标（总页数、平均秒/页、元素构成） | 写报告引用结论 |
| `docs/enterprise-upgrade-plan.md` | 结论回填后的正式方案 | 架构决策依据；吞吐表已从"估算"升级"实测" |

**待办清单的含义**——每个待办对应一个尚未验证的假设：

- 扫描件样张：语料全是数字原生，"OCR 兜底"目前只在 6 张图上验证过，没在真扫描件上验证；
- TableFormer 关闭对照：现在只知道"版面+表格合计 4.4s"，不知道两者各占多少——再做一轮 `do_table_structure=False` 对照就能拆开；
- GPU 验证：5-10 倍是行业经验值，本机 5060 的实际数字没测；
- PaddleOCR-VL 对比：VLM 路线 vs 传统管线的质量对比，原方案遗留项。

## 复习要点（本篇的核心三句话）

1. **Docling 的成本结构**：版面模型 + TableFormer（每页必跑的深度学习推理）>> OCR（数字原生文档上趋近于零）——所有吞吐优化都应该冲着前者去；
2. **归因靠对照实验，不靠直觉**：改一个变量跑两轮，差异就是那个变量的贡献；
3. **架构应对是分流而不是堆资源**：先问"这份文档值得上全管线吗"，再问"要不要买更多算力"。
