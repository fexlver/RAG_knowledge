# 2026-08-21 · 上传透明化 + 表格感知切块 + 向量升级（v4@2048）

> 对应提交：`feat: 上传后台任务化与进度透出，表格按行切块，embedding 升级 2048 维`
> 触发诉求：上传后在界面上"有没有正确写入"完全不可知；Docling 管线一次解析十几分钟，同步等待的连接模式彻底不可用。

## 做了什么

三件事，一次提交完成：

1. **上传入库后台任务化**：`POST /api/documents` 不再同步阻塞到入库完成，而是立即返回 `job_id`（HTTP 202）；真正的解析、向量化、写索引进后台线程，新增 `GET /api/documents/upload-jobs/{job_id}` 供轮询。前端知识库页轮询并渲染每个文件的阶段徽标（排队中/解析文档/生成向量/写入索引/完成/跳过/失败）、总进度条、块数、解析器名与耗时。
2. **表格感知切块**：超过 `CHUNK_SIZE` 的长表格不再被通用递归切分从中间劈开，而是**按行边界拆分、每个片段重复表头**（列名行 + `|---|` 分隔行），片段脱离上下文也能读懂。
3. **embedding 升级**：`text-embedding-v4` 从 1024 维升到 2048 维（该模型参数上限），Milvus collection 从 `food_safety_chunks_v2` 换到 `_v3`（维度建表时固定，只能换表）。`.env.example` 同步更新并注明换表原因。

## 用了什么技术

- **后台任务 + 轮询，而不是 SSE**：上传是"提交-慢慢干"型长任务，SSE 要求连接一直保持，浏览器刷新/合盖就断；轮询是无状态轮询，页面刷新后凭 job_id 恢复。任务记录在内存里保留 1 小时（`UploadJobManager`，daemon 线程 + 到期清理）。
- **进度回调穿透三层**：`ingest(progress=cb)` -> `report(stage, detail)` 在解析/向量化/写入三个阶段回调 -> `UploadJobManager._advance` 写进 `FileProgress`（dataclass，非锁保护的单写者模型：只有任务线程写，API 线程只读，GIL 下安全）。
- **全局互斥串行入库**：`threading.Lock` 包住 `ingest()`，同一时刻只跑一个入库任务。Docling 版面模型本来就把 CPU 吃满，并发只会互相拖慢 + 内存翻倍。
- **行边界表格拆分**：用 `|---|` 分隔行识别 markdown 表头，预算 = `chunk_size - 表头长度`，逐行累加超预算即切一片、带上表头。找不到标准表头时退回通用递归切分（保守降级）。
- **embedding 维度参数**：DashScope `text-embedding-v4` 的 `dimension` 参数直接传 2048，客户端早已支持（`qwen_gateway.embed_documents`），只改配置默认值。

## 解决了什么问题（效果怎么样）

- **“上传后不知道发生了什么”**：之前同步接口在 Docling 管线下长时间无响应（大文件 10 分钟级），前端只有“正在处理…”。现在提交后 1 秒内返回，每个文件的阶段、块数、解析器、耗时、失败原因全部可见。实测（东吴证券 2023 年报，748KB）：**95.1 秒完成全链路**（docling 解析 -> 65 块 -> v4@2048 向量化 -> 写入 v3），阶段流转 解析文档(约40s) -> 生成向量 -> 写入索引 -> 完成 全程正确；随后用“2023 年营业收入和净利润”提问，答案精确（112.81 亿/20.02 亿）并给出 **5 条引用**，全部指向该年报且带页码与章节路径（首条引用正是 docling 解析出的“3.1 主要会计数据”表格块--表格进检索的价值直接兑现）。
- **"表格 markdown 信息密度高，怕 token 超限"**：长表拆成多个带表头的小片段，单个 chunk 的字符数受 `CHUNK_SIZE` 硬约束，embedding 输入长度风险消除；同时表头重复保证了每个片段的语义完整性（"金额"这一列单独出现没有意义，"本期金额"才有）。
- **"Milvus 旧 schema"**：确认 locator 走 JSON 字段、`element_ids` 不需要 schema 变更；真正必须换表的只有维度。换 `_v3` 后旧 `_v2` 保留在库中（孤儿表，可手动删），旧文档需重新上传才能在新维度下检索。
- 测试：后端 **41 passed**（新增 `test_upload_jobs.py` 3 个：阶段推进顺序、单文件失败不阻断后续、预失败条目跳过处理；`test_api.py` 增加端点集成测试；`test_structured_document.py` 增加长表拆分/短表保持 2 个），前端 **10 passed**（vitest），`npm run build` 通过。

## 遇到的问题与该怎么办

| 问题 | 根因 | 应对（通用方法） |
| --- | --- | --- |
| curl 上传中文文件名变乱码（`¶«ÎâÖ¤È¯`） | Git Bash（GBK 控制台）把 `;filename=` 参数按 GBK 字节发给 curl，multipart 头里就是 GBK，服务端按 UTF-8 解码失败 | 换 Python `requests` 上传（UTF-8 可控）。**浏览器是 UTF-8 不受影响，这是纯命令行工具问题**。方法：Windows 下做中文文件名的接口测试，别用 curl，用 requests/httpx |
| 第一次后台起服务的任务显示 "failed exit code 1" | 是被我 `taskkill` 重启杀掉的旧进程，不是真故障 | 判断后台任务失败先看是不是人为终止；看 `output/app-7860.log` 里的 uvicorn 启动日志确认现进程健康 |
| 任务式接口的竞态断言 | 后台线程可能在 POST 响应返回前就跑完（测试里 fake ingest 极快），"返回时 status 必为 running / finished_files 必为 1" 这类断言随机挂 | 轮询到终态再断言终态；不断言中间态的精确值。**方法：并发场景的测试只断言不变量（最终态、内容），不断言时序** |
| 任务里的临时文件生命周期 | 同步版在 `finally` 里删临时文件；后台版响应先返回，`finally` 时序失效 | 临时文件清理责任移交给任务线程：`_run` 的 `finally` 里删文件、删空目录；API 层只负责保存失败时的兜底清理 |
| 2048 维换表后旧文档检索不到 | 维度是建表属性，新旧向量不通用 | 接受重建成本（单机开发环境）：旧 collection 保留、重新上传文档进 `_v3`。`.env.example` 注释写明"维度变更需新 collection + 重传" |
