# 2026-08-20/21 · 企业升级方案评审与修订

> 产出：`docs/enterprise-upgrade-plan.md`（含【修订】标注与实测回填）

## 做了什么

评审和 Codex 讨论出的初版企业级升级方案（内部私有化、部门试点、20-50 人并发、1万-10万份文档、完全离线、RTX 5060 8G），逐条给出修订意见并整理成正式方案文档。参考了知乎一篇讲文档解析的文章（对比 OCR 主链路 vs VLM 解析的路线之争）。

## 用了什么技术（决策涉及）

- Milvus 2.5+ 内置 **BM25 全文检索**（jieba analyzer）--替代独立 OpenSearch；
- Docling + RapidOCR（PaddleOCR 模型的 ONNX 封装）--OCR 主链路；
- PaddleOCR-VL（0.9B 文档解析 VLM）--按需增强，不进主链路；
- ACL 冗余进 Milvus **标量字段**做检索预过滤；
- tombstone（墓碑标记）+ 异步索引清理--删除一致性；
- 渐进式索引 + 原子索引版本切换。

## 解决了什么问题（关键修订与理由）

1. **砍掉 OpenSearch**：Milvus 2.5+ 自带 BM25（支持 jieba 分词），再引入一个独立搜索引擎只增加运维成本和一致性负担。离线内网场景组件越少越好。
2. **解析验证提前为 Phase 0**：解析质量是全系统最高技术风险、验证成本最低。先花一周拿真实样张量化解析质量，再决定 Element 数据模型字段和切块策略，避免先迁移数周基础设施后发现解析不达标要回改数据模型。
3. **ACL 用标量冗余而非文档服务过滤**：检索时在 Milvus 表达式里直接 `permission in (...)` 预过滤，避免"先召回再过滤"导致的召回截断和权限泄露窗口。
4. **删除一致性用墓碑**：删除请求立即写墓碑（检索侧立刻不可见），物理清理由异步任务做，保证"删除后不可见"的强一致语义。
5. **渐进式索引**：文本索引先上线可检索，OCR 修正与 VLM 增强异步补充，最慢环节不阻塞可用性。
6. **写死吞吐预算表**：每个环节单页成本 -> 全量估算 -> 加速手段，让"能不能在窗口期建完库"变成可计算的问题。（后来 Phase 0 实测证明这步做对了，见 2026-08-21 spike 日志）
7. **补齐评测体系**：解析质量、检索（召回/MRR）、拒答正确率、引用忠实度分阶段挂验收，每次解析器/切块/检索策略变更跑回归。

## 效果怎么样

- 方案从"功能清单"变成"分 6 个 Phase、每期带验收标准的可执行路线"；
- 吞吐预算表在 Phase 0 实测后回填了真实数据，修正了 10 倍量级的估算偏差；
- 明确了多模态的实现方式：首期用"投影"（图片/表格转文字证据喂给纯文本生成模型），不急着换多模态生成模型。

## 遇到的问题与该怎么办

| 问题 | 应对 |
| --- | --- |
| 知乎文章 WebFetch 直接 403 | 用浏览器标签页导航 + evaluate 提取正文。**方法：反爬站点换浏览器渠道，别硬刚 HTTP** |
| 初版方案没有数据支撑的吞吐估算 | 修订版强制"预算表必须实测回填"（后来 spike 真的测了，发现数字原生解析实测 4.4s/页 vs 估算 0.1-0.5s/页） |
| 讨论时功能越堆越多（音频、跨模态、语义缓存） | 修订时全部标成"第二期插件"或"按需"，首期收敛到 PDF/Word/Excel/图片 + 文本问答主链路 |

## 复习要点

评审一份技术方案时的检查清单（这次实际用到的）：

1. 最高风险、最低验证成本的事，应该最先做（所以解析提前到 Phase 0）；
2. 每个组件引入前问"它解决了什么现有组件解决不了的问题"（OpenSearch 被砍的原因）；
3. 吞吐/存储估算要有数字，且标明是估算还是实测；
4. 一致性语义（删除、权限、版本切换）要显式设计，不能靠"应该没问题"；
5. 多模态这类大特性，先用"投影"这类低成本方式拿到 80% 收益。
