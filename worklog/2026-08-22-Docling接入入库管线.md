# 2026-08-22 · Docling 接入入库管线（双解析器并行可选）

> 对应提交：`61ad9ad feat: Docling 解析器接入入库管线`；对比报告 `output/parser-comparison/000010_美丽生态_2023.md`

## 做了什么

把 Phase 0 验证过的 Docling 解析能力接入现有入库链路，作为**与 PyMuPDF 并行的可选解析器**（不是替换）：默认行为完全不变，`.env` 里 `PDF_PARSER=docling` 一行切换。附带一份真实年报的双管线切块质量对比报告。

## 用了什么技术

- **协议适配**：实现另一个会话留下的 `DocumentParser` 协议（`supports`/`parse`/`name`/`version`），产出统一的 `ParsedDocument`--下游切块、artifact 落盘、evidence window 零改动；
- **按名解析 + 懒加载**：`ParserRegistry.parse(path, parser_name=...)`；docling 依赖重（torch 全家桶），只在显式选择时才 import；
- **配置开关**：`Settings.pdf_parser`（env `PDF_PARSER`，默认 `pymupdf_text`），且**只作用于 PDF**，TXT 等继续按扩展名自动路由；
- **坐标转换**：Docling 的 prov bbox（PDF 磅、底左原点）→ 前端高亮矩形（0–1 归一化、顶左原点）；
- **表格进检索**：TableItem 导出 markdown 作为元素内容，块内容即表格投影。

## 解决了什么问题（效果怎么样）

同一份年报（175 页/360 表）两条管线的切块对比：

| 指标 | pymupdf_text | docling |
| --- | --- | --- |
| 解析耗时 | 0.6s | 955.4s |
| 表格元素数 | 0 | 359 |
| 文本块数 | 770 | 1221 |
| 平均块大小 | 201 字符 | 345 字符 |
| 带章节路径 / 高亮矩形 | 100% / 100% | 100% / 100% |

质量差异的直观例子--同一块"公司信息"区域：

- pymupdf 输出：`股票简称\n美丽生态\n股票代码\n000010\n...`--表格结构全丢，键值对应关系消失；
- docling 输出：`| 姓名 | 陈美玲 | 何婷 |`--markdown 表格完整保留，"董事会秘书叫什么"这类问题的证据质量完全不同。

其他收益：docling 的标题元素是模型判定的（646 个），比 pymupdf 管线的启发式（703 个，含表格短行误判）更准；块更大更完整（345 vs 201 字符），因为表格不再被行切块切碎。测试 **35 passed**，docling 未安装的环境自动跳过（`pytest.importorskip`）。

## 遇到的问题与该怎么办

| 问题 | 根因 | 应对（通用方法） |
| --- | --- | --- |
| 加了 `Settings.pdf_parser` 字段后 3 个测试挂 | 直接构造 `Settings(...)` 和 `SimpleNamespace` 伪造 settings 的测试没传新字段 | 新配置字段给**默认值**（dataclass 移到末尾）；伪造对象补字段。**方法：给共享模型加字段时，先 grep 所有构造点，并尽量带默认值** |
| `解析器 pymupdf_text 不支持 .txt 文件` | `pdf_parser` 语义是"PDF 解析器"，却在所有文件类型上生效 | service 层按扩展名限定：只有 `.pdf` 才传 parser_name。**方法：配置项的名字要圈定作用域，注入点再显式限定一次** |
| 单测抓到矩形 top > bottom | 底左原点下 `t > b`（顶边离页底更远），我换算时把 t/b 当成了 top/bottom 直接用反 | 修正是 `top = height - t, bottom = height - b`。**方法：坐标转换必须写"方向断言"（top < bottom、0 ≤ v ≤ 1）的单测，这次就是它抓出来的** |
| traceback 显示 C: 盘旧路径，疑似跑错仓库 | 迁移时把 C: 编译的 `__pycache__` 一起拷了过来，.pyc 里嵌的 co_filename 是旧路径；两边源文件内容相同所以校验通过、正常执行 | 删掉项目内陈旧 `__pycache__`。**方法：迁移项目后清一遍 `__pycache__`；看到"路径诡异但行为正常"先怀疑字节码缓存** |
| 对比脚本 `DocumentMetadata` 构造参数错 | 凭记忆写了 `doc_id/file_name`，实际是 `source` | 改成 `source=name`。**方法：调用不熟悉的 dataclass 前先 grep 定义** |

## 复习要点

1. **适配器模式的价值**：因为有统一 `DocumentParser` 协议，接 docling 只写了一个新文件 + 一处注册，下游零改动--先定协议再接实现，扩展成本最低；
2. **灰度切换的设计**：默认不变 + 显式开关 + 按类型限定作用域 + 懒加载重依赖，四个手段让"引入 3GB 依赖"对存量系统零影响；
3. **对比实验再次立功**：表格元素 0 vs 359、块均 201 vs 345 字符，质量收益和 0.6s vs 955s 的代价都量化了，"值不值"从观点变成算术。
